# 官方战斗模型 getter 索引 → 本仓对照表

- 日期：2026-09-13　配套：`docs/obs-suite-analysis-2026-09-13.md`
- 用途：把 obs 里零散的**官方战斗类 getter/setter** 索引成一张表，标明「官方类.成员 ↔ CS 2.7.71 声明行 ↔ 本仓落点」，
  用于①校验结算字段语义、②评估补全战斗实现时要读客户端哪些状态、③判断某个概念本仓是否已有对应类型。
- 真值源：`reference/obs/OpenBachelorC-master.zip` 的 `rel/trainer.js`（17 组作弊命令背后即这些 getter）、
  `reference/obs/OpenBachelorInsight-master.zip` 的 `src/inject/*.ts`（hook 点）、CS 签名文件
  `reference/com.hypergryph.arknights_2.7.71.cs`（行号以该版本为准，客户端更新后需重跑 `pnpm run decompile`）。

## 0. 结论先看

1. **本仓没有服务端战斗模拟**：`app/game/modules/battle/battle.ts` 的 `BattleManager` 只做
   **结算校验 + 奖励/掉落发放**（客户端权威），因此下表的官方运行时 getter 绝大多数**服务端不读**，
   只能从客户端上报的聚合统计（`BattleStats`，见 `app/game/kernel/battle-model.ts:24-99`）间接获得。
2. **可立即用于校验的两处**：`EnemyDuel` 结算的 `surviveUnits/bornUnits`（本轮已类型化，
   见 `docs/obs-可借鉴清单-2026-09-13.md` §1.1）与 `BattleStats.enemyStats/killedEnemiesCnt`。
3. **补全战斗实现**时，下表「CS 声明」列是权威字段序/类型来源；不要照抄 obs 的 JS hook 名当协议。

## 2. Insight 的两个 hook 点

| hook | 用途 | 与本仓的关系 |
| --- | --- | --- |
| `Torappu.Battle.Scheduler._OnActionExecuted` | 战斗调度动作级 trace（可复现战斗过程） | 本项目无服务端战斗调度；仅作分析参考 |
| `Torappu.DataCenter.EnemyDuelDataCenter.AddTeamData` | 读 `teamLeft/teamRight` 的 `enemyId`+`count`（右阵营计负数） | 直接对照 EnemyDuel 结算的 `bornUnits`（`activity.schema.ts` 已类型化） |

Insight 抓包 `data/*.jsonl` 证明：**同一 `stage_seed` 下回合结果可复现**
（`round_0..9_seed` + `round_N_victor`，1=左胜、2=右胜）。可用于复现/自测；
**不要**用于官方对局胜率预测下注（红线，见 `docs/obs-可借鉴清单-2026-09-13.md` §5）。

## 4. 复跑命令

```bash
# 确认某 getter 在当前客户端的存在与签名（CS 签名文件由 pnpm run decompile 生成）
grep -n "get_lifePointReduce(" reference/com.hypergryph.arknights_2.7.71.cs

# 抽取 obs 的 hook 源码
python3 - <<'EOF'
import zipfile, os
zf, prefix, dst = 'reference/obs/OpenBachelorInsight-master.zip', 'OpenBachelorInsight-master/', 'tmp/obs-analysis/insight'
z = zipfile.ZipFile(zf)
for n in z.namelist():
    if n.startswith(prefix) and not n.endswith('/'):
        out = os.path.join(dst, n[len(prefix):]); os.makedirs(os.path.dirname(out), exist_ok=True)
        open(out, 'wb').write(z.read(n))
EOF
```
