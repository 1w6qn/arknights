## 2. 链路（四步）


## 3. 关键实测事实（本轮）

1. **内置 bundle 名逐版本变化**：2.7.61 为 `anon/7d91430e114d86fef7d3b3511151e12d.bin`，2.7.71 为
   `anon/3ea52f7d41a320d200aa7e61735f0819.bin` —— 链路全程按锚点资产（entry/DefinedFix）探测，无硬编码。
2. **该 bundle 出现在 `assets/AB/Android/hot_update_list.json` 的 `abInfos`**（`hash`/`md5` = `d21c`，
   `totalSize`/`abSize` = 1111710）。私服在 `assets.enableMods` 打开时会重写该清单并追加 mod 条目
   （`app/ops/assets/asset.ts:44`），因此回灌后即使客户端判定本地资源“过期”，重新拉到的也是**同一份 mod**。
3. **官服域名不在 `global-metadata.dat`**（`ak-conf.hypergryph.com` 命中 0），而落在
   `assets/bin/Data/sharedassets1.assets.split14` 的 Unity 字符串表（长度前缀 + 4 字节对齐）里；
   4 处 `hypergryph.com` 命中均为开发期域名残留（`an-1-bus…`、`10.154.0.24:5000`）。
4. **APK 结构**：3688 条目（5 dex / 51 so / 2435 `.ab` / 95 `.bin`），原包 V1(JAR) + V2/V3(APK Signing Block) 双签名；
   772 个条目使用数据描述符（bit3）；无 zip64。
5. 内置 bundle 条目为 **STORED**（method 0），替换后体积 +41,292 B → 其后所有条目偏移整体位移，
   故重写时必须重做对齐（本工具按 STORED 4 字节、`.so` 4096 字节重排）。

## 8. MuMu 模拟器调试实录（2026-09-13）

环境：MuMu 12 明日方舟定制版（`D:\Program Files\YXArkNights-12.0`，Android 12 / API 32，x86_64 + Houdini
ARM 翻译）；adb 端口 `127.0.0.1:16384`（`MuMuManager.exe adb -v 0`），adbd 已是 root。

### 8.1 关键结论：Lua 引导 bundle 必须从 **APK 内** 加载

- 客户端把 `gamedata/[uc]lua/*` 解析到**热更 resVersion 对应的 bundle 名**：
  2.7.71 为 `anon/63bbacd2fab677125a1516d4396114ab.bin`（**不是** APK 内置的 `anon/3ea52f7d….bin`）。
- 该 bundle 走 **APK 内路径**（日志：`Can not load assetbundle: jar:file://…base.apk!/assets/AB/Android/anon/63bbacd2….bin`）。
  放进 `files/Bundles/anon/` 持久目录、**即使登记进 `persistent_res_list.json` 也不会被使用**
  （同路径放官方原包同样报 `Failed to load asset`，可作对照）。
- ⇒ 改包必须用 `apk:patch --add` 把注入版 bundle **新增**为 APK 内的同名条目，替换旧内置 bundle（`3ea52f7d…`）无效。

### 8.2 重打包必须保留的四件事（缺一即加载失败或崩溃）

| 项 | 缺失症状 | 处理 |
| --- | --- | --- |
| **AssetBundle(142) 容器**（key = `dyn/gamedata/[uc]lua/<小写相对路径>.lua.bytes`） | `Failed to load asset: gamedata/[uc]lua/entry.lua`（Unity 无法按名解析） | 从官方 bundle 继承 key（按 basename 与对象一一对应）；插件新增资产按同一命名法派生 |
| **64 位 pathId**（官方为散列值，> 2^53） | 同上（清单按 pathId 寻址） | `extractBundleWithMeta` 全程 bigint；曾因 `Number(pathId)` 丢精度导致全部资产查不到 |
| **官方类型表**（`enableTypeTree=true`） | 容器字段序被 Unity 内置类型读错 → 查找失败 | 原样写入官方类型表字节 |
| **对象数据起点 8 字节对齐** | `libunity.so` SIGSEGV（UnityMain 崩，日志 `#00 pc … libunity.so`） | 对象之间零填充对齐到 8（官方 345 个对象全部 8 对齐）；另需避免新资产与 AssetBundle 对象 pathId 撞号 |

`apk-patch --add` 另有细节：新增条目的 DOS 时间戳不能用 0（月份/日期为 0 属非法值）。

### 8.3 Frida 在 MuMu 的可为与不可为

- **不可为**：ARM 翻译层下 `libil2cpp.so` / `libunity.so` 是 guest 模块，宿主 Frida 的模块枚举看不到
  （`Process.findModuleByName("libil2cpp.so")` 恒为 null）→ 原生 il2cpp 级 hook（如 `AssetBundle.LoadAsset`）不可用。
- **可为**：宿主 `libc.so` 的 `__android_log_print` 等 log 出口可 hook，**日志流式查看可用**：
  frida-server(x86_64) 推入设备（`/data/local/tmp/frida-server -l 127.0.0.1:27042`）→ Windows 侧
  `adb forward tcp:27042 tcp:27042` + `node tmp/port-relay.mjs 27043 27042`（WSL 访问）→
  `python3 scripts/frida-log.py --target <包名|pid>`。
- **坑**：进程名是中文「明日方舟」，不等于包名 → 按进程名 attach 会 `ProcessNotFoundError`，需先 `pidof` 再按 pid attach。
- `scripts/frida-log.py` 默认 attach 模式只挂 4 个模块的 log 出口（`--spawn` 全模块 648 个 hook 会让 frida-agent 在早期初始化时 SIGSEGV）。

### 8.5 插件下发方式修正：内联 `package.preload`（推荐），而非新增资产

实测发现：即使把插件资产加进 bundle 并补上容器 key，客户端仍拿不到它们——**客户端的资源清单（`*.idx`）
按 pathId 寻址**，清单里没有新增资产 → 插件路径（`gamedata/[uc]lua/Plugin/*.lua`）无法解析。

而引擎的热修管线是**纯 Lua**：`entry.lua` → `require("Hotfixes/DefinedFix")` → `HotfixProcesser.Do(fixes)`
（见内置 bundle 内的 `HotfixProcesser.lua`：`local cls = require(v)`）。Lua 的 `require` **先查
`package.preload`**，再走 XLua 的 CustomLoader（资产查找）。

⇒ `repack:lua --inline-plugins`：把 `lua/plugin/*.lua` 内联为
`package.preload["Plugin/<X>"] = function(...) … end` 追加到 **entry.lua**（清单已知资产，容器/pathId 不变），
插件资产**不再新增**（bundle 资产数保持 344，只多一个变大的 entry.lua）。DefinedFix 仍注入
`"Plugin/PluginBootHotfixer"` 条目，引擎 require 时命中 preload → 插件系统启动。

内联版默认写落盘埋点（`Application.persistentDataPath/plugin_boot_trace.txt`，包名无关）：
`preload registered` 证明 entry.lua 执行到注入代码，`PluginBootHotfixer required` 证明热修管线确实加载了插件引导。

### 8.6 为什么「把注入版 bundle 塞进 APK」仍不够：客户端会用热更清单覆盖它

实测（MuMu 12 / 2.7.71）：把注入版 Lua bundle 放进 APK 后启动，客户端会在 `files/Bundles/anon/`
**主动重新下载官方同名 bundle**（`anon/63bbacd2….bin`，1,121,653 B），覆盖 APK 内那份（1,213,360 B）：

```
# 启动瞬间（20:18）观察到的落盘
-rw-rw---- 1 u0_a37 ext_data_rw 1121653 20:18 63bbacd2fab677125a1516d4396114ab.bin
```

原因：该 bundle 在 `hot_update_list.json` 的 `abInfos` 里有 `totalSize/abSize` 记录，客户端按清单校验，
尺寸不符即判定「需更新」并重新拉取（`hash/md5` 为固定的 4 位短值，非内容摘要，故尺寸是主要判据之一）。
把设备端缓存清单的该条目改成我方尺寸后，客户端不再下载，但也**没有加载 Lua**——因为它此时卡在
热更/SDK 流程（`HGGameUpdateSDK.GetLatestGame` → 等待），Lua 阶段尚未到达（早期几次能走到 Lua 阶段，
是因为当时应用数据里已有「热更已完成」的状态）。

⇒ 结论（下一轮入口）：**必须先让客户端整体指向私服**（`network_config` → `hu` → 官方 CDN 全部换成私服），
之后服务端重写的 `hot_update_list.json`（含 mod 条目）+ `mods/*.dat` 才会自然生效，插件也才会随 Lua bundle 加载。
在 MuMu 上使客户端改向有两条路：
1. **APK 字串等长改写**（`sharedassets1.assets.split14` 内 `https://ak-conf.hypergryph.com/...` → `http://<等长主机名>/...`
   + 设备 `/etc/hosts` 指向 127.0.0.1 + `adb reverse tcp:80 tcp:8443`）——不依赖 Frida，最稳；
2. **Frida C# 级 hook**（`hook/main.ts` 的 `Networker.get_overrideRouterUrl`）——但 MuMu 的 ARM 翻译层下
   `libil2cpp.so` 是 guest 模块，宿主 Frida 枚举不到（见 §8.3），需按内存扫描定位，成本更高。

### 8.7 硬约束一：MuMu 上被重签名的 APK 会被反外挂杀掉（ACE/TSS）

同一台 MuMu 12 上对照实验：

| 包 | 结果 |
| --- | --- |
| `com.hypergryph.arknights`（官方原包，未改动） | 正常运行 ✓ |
| `com.hypergryph.arkmumu12`（改名 + debug 重签 + 注入 bundle） | 过用户协议后 `Fatal signal 11`，tombstone 栈全部落在 `lib/arm64/libtersafe2.so`（腾讯 TSS/ACE）✗ |

```
F DEBUG : #00 pc 00000000001fb9dc  .../lib/arm64/libtersafe2.so
F libc  : Fatal signal 11 (SIGSEGV) ... pid 16025 (gryph.arkmumu12)
```

即 **ACE 对改包做自校验并主动终止进程**。按本仓红线（`docs/no-root-injection-chain-2026-09-13.md` §7），
不做反外挂绕过；因此「改包 + 重签名」在 MuMu 上无法跑到插件启动。

### 8.8 硬约束二：客户端会删掉「被替换」的 Lua bundle

三种替换方式都被客户端拒收（启动后文件被删除或覆盖）：

1. 把注入版 bundle **新增进 APK**（`anon/63bbacd2….bin` 1,213,360 B）→ 客户端按热更清单判定需要更新，
   从官方 CDN **重新下载**官方版（1,121,653 B）覆盖；
2. 放进持久目录 `files/Bundles/anon/`（并把缓存清单尺寸改成我方值）→ 启动即被**删除**；
3. 只在 APK 里提供（删掉持久副本）→ 不报错也不加载（既不崩也无埋点）。

⇒ 判定不只依赖 `hot_update_list.json` 的 `abSize`（`hash/md5` 为固定 4 位短值、非内容摘要），
疑似还比对 `*.idx` manifest（34 MB 二进制，按 pathId 记录资产）。**只有「客户端自己按服务端清单下载」的
mod（`mods/*.dat`）路径会被接受**——也就是必须先让客户端整体改向私服。

### 8.9 本轮结论与下一轮入口

- 等长 URL 改写链路本身已验证可用：`apk:url-redirect` 改写 `sharedassets1.assets.split14` 的
  `https://ak-conf.hypergryph.com` → `http://ak-confx.hypergryph.com`（等长），设备侧
  `/etc/hosts` 指向 127.0.0.1 + `adb reverse tcp:80 tcp:8443` 后，**设备内 curl 该域名直接拿到私服响应（200）** ✓。

- 另一条 ACE 安全路线（不改 APK、不碰反外挂）：**MITM 官方 CDN（`ak.hycdn.cn`，HTTPS）**
  - 设备 root：把自签 CA 装进系统信任库（`/system/etc/security/cacerts` bind-mount）+ `/etc/hosts` 指向 127.0.0.1；
  - 本机：443 端口跑一个 TLS 代理，对
    `/assetbundle/official/Android/assets/<ver>/hot_update_list.json` 返回**改写后的清单**（含我方 bundle 尺寸），
    对 `.../anon/63bbacd2….bin` 返回**内联插件版 bundle**，其余请求透传真实 CDN；
  - 官方包（ACE 可过）热更后即加载插件 → 插件接管网络（含 RSA 验签绕过）→ 私服流程成立。
  - 风险：`HGDownloadSDK`（Java/okhttp）若有证书固定则此路也不通，需先做最小验证（TLS 握手能否被接受）。
